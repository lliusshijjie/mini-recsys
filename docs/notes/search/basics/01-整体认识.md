# 搜索引擎整体认识

## 1. 搜索引擎是什么

搜索引擎本质上是一个：

> 根据用户输入的 Query，从海量内容中快速找到相关结果，并按照一定规则进行排序的系统。

对于一个 App 来说，用户在搜索框中输入：

```text
无线降噪耳机
```

搜索系统需要解决三个问题：

1. 用户真正想找什么；
2. 哪些内容可能符合需求；
3. 这些内容应该按照什么顺序展示。

因此，搜索并不是简单地在数据库中执行字符串匹配，而是一条包含理解、召回、排序和结果组装的完整处理链路。

------

## 2. 一次搜索请求的基本流程

用户输入 Query 后，系统通常会经历下面几个阶段：

```text
用户输入 Query
    ↓
请求接入
    ↓
Query 理解
    ↓
多路召回
    ↓
候选合并与去重
    ↓
粗排
    ↓
精排
    ↓
业务重排
    ↓
结果组装
    ↓
返回 App
```

### 2.1 请求接入

搜索请求首先进入网关或搜索服务入口，完成：

- 鉴权；
- 限流；
- 日志记录；
- Trace ID 生成；
- A/B 实验分桶。

这一阶段主要负责保护系统和记录请求上下文。

### 2.2 Query 理解

用户输入往往不够规范，例如：

```text
苹果15壳
蓝牙耳鸡
```

系统需要进行：

- 文本规范化；
- 中文分词；
- 拼写纠错；
- 意图识别；
- 品牌、型号、类目等实体抽取；
- 同义词扩展和 Query 改写。

例如：

```text
苹果15透明壳
```

可能被解析为：

```text
品牌：苹果
型号：iPhone 15
类目：手机壳
样式：透明
```

### 2.3 多路召回

召回阶段的目标是：

> 从海量数据中快速找出一批可能相关的候选内容。

常见召回方式包括：

- 倒排索引召回；
- 向量语义召回；
- 类目和属性召回；
- 热门内容兜底；
- 业务规则召回。

这些召回通道通常并行执行，以降低整体延迟。

### 2.4 排序

召回得到的候选数量仍然较多，因此需要继续排序。

```text
海量文档
    ↓
召回几千个候选
    ↓
粗排保留几百个
    ↓
精排保留几十个
```

粗排强调计算速度，精排则会使用更多特征，例如：

- Query 与文档的相关性；
- 用户兴趣；
- 点击率和转化率；
- 内容质量；
- 热度和新鲜度；
- 业务价值。

### 2.5 重排

精排结果还不能直接展示，因为可能出现：

- 同类内容过多；
- 同一店铺连续出现；
- 无库存商品排名过高；
- 结果缺乏多样性；
- 需要插入广告或业务内容。

重排阶段会在相关性基础上加入业务约束和多样性控制。

## 3. 搜索系统中的调度

搜索请求背后存在多种调度。

### 服务调度

请求会经过多个服务：

```text
网关
→ Query 理解服务
→ 召回服务
→ 排序服务
→ 文档服务
```

### 分片调度

索引数据通常分布在多台机器上。

```text
搜索协调节点
    ├── 索引分片 1
    ├── 索引分片 2
    ├── 索引分片 3
    └── 索引分片 N
```

协调节点会并行查询多个分片，然后归并各分片返回的局部 TopK。

### 异步任务调度

在 Tokio 服务中，多路召回通常通过：

```rust
tokio::join!
```

并发执行。

网络 RPC、Redis 查询和索引服务调用适合使用异步方式；粗排、重排和模型推理等 CPU 密集任务，则应该放入独立线程池或使用：

```rust
tokio::task::spawn_blocking
```

避免阻塞 Tokio Runtime。

### Deadline 调度

整个搜索请求通常有统一的时间预算。

```text
Query 理解：若干毫秒
召回：若干毫秒
排序：若干毫秒
结果组装：若干毫秒
```

如果某个召回通道或索引分片超时，系统通常不会一直等待，而是使用已有结果继续返回。

## 4. 工业搜索引擎的主要难题

### 4.1 Query 理解困难

用户输入可能很短、模糊、有错别字，也可能包含品牌、型号、缩写和口语表达。

搜索系统需要尽可能准确地理解真实意图。

### 4.2 召回率和准确率难以平衡

召回范围太小，容易漏掉相关结果；召回范围太大，又会引入大量无关内容。

搜索系统通常使用倒排索引和向量召回相结合的方式。

### 4.3 海量数据下保持低延迟

搜索可能需要查询数千万甚至数十亿条数据，但用户希望快速得到结果。

系统需要处理：

- 分布式索引；
- 并行查询；
- 缓存；
- TopK 归并；
- 超时；
- 降级；
- 慢节点。

### 4.4 索引实时性

商品、文章和视频会不断新增、删除和修改。

搜索引擎需要让这些变化尽快反映到搜索结果中，同时保证多个索引分片之间的数据一致性。

### 4.5 排序目标复杂

搜索排序不仅要考虑文本相关性，还要综合：

- 用户点击概率；
- 内容质量；
- 新鲜度；
- 转化率；
- 用户个性化；
- 商业收益。

这些目标之间经常相互冲突，因此需要多目标排序和业务重排。

## 5. 常见搜索引擎框架

### Elasticsearch

Elasticsearch 是工业界最常见的分布式搜索引擎之一。

它提供：

- 全文检索；
- 倒排索引；
- 分布式分片；
- 聚合分析；
- REST API；
- 集群扩容；
- 向量搜索。

适合：

- 电商搜索；
- 站内搜索；
- 日志分析；
- 内容检索。

### Apache Solr

Solr 同样基于 Apache Lucene，属于成熟的企业级搜索平台。

它支持：

- 全文搜索；
- Facet；
- 高亮；
- 分布式索引；
- 结构化查询。

Solr 在传统企业搜索系统中较为常见。

### OpenSearch

OpenSearch 是开源搜索与分析平台，整体定位与 Elasticsearch 类似。

它支持：

- 关键词检索；
- BM25；
- 向量检索；
- 分布式搜索；
- 数据分析。

常见于开源方案和云服务场景。

------

## 6. Tantivy 的定位

Tantivy 是一个使用 Rust 编写的全文检索库，设计思想类似 Apache Lucene。

它提供：

- 倒排索引；
- BM25 排序；
- 分词器；
- TopK 查询；
- Facet；
- 模糊查询。

但 Tantivy 本身更接近一个搜索内核，而不是完整的分布式搜索平台。

```text
Lucene / Tantivy
    ↓
搜索引擎核心库

Elasticsearch / Solr / OpenSearch
    ↓
完整搜索服务和分布式平台
```

Tantivy 默认不会自动提供：

- 集群管理；
- 索引分片；
- 副本和容灾；
- 跨节点查询；
- REST 搜索服务；
- 分布式 TopK 归并。

这些能力需要开发者自行构建，或者使用基于 Tantivy 的上层搜索系统。

对于 Rust 项目，可以采用：

```text
Axum
    ↓
Query 解析
    ↓
Tantivy 关键词召回
    ↓
HNSW 向量召回
    ↓
结果融合和排序
    ↓
返回搜索结果
```

这种方案适合学习搜索引擎内部结构，也适合构建可控、轻量、嵌入式的搜索服务。

## 7. 搜索引擎与推荐系统的关系

搜索系统和推荐系统的整体流程很相似：

```text
召回
→ 粗排
→ 精排
→ 重排
```

主要区别在于入口信号不同。

### 搜索系统

主要依赖用户主动输入的 Query：

```text
用户明确表达当前需求
```

### 推荐系统

主要依赖用户历史行为和画像：

```text
系统推测用户可能喜欢什么
```

现代 App 中，两者往往共享很多基础设施：

- 用户画像；
- 特征平台；
- 向量检索；
- 排序模型；
- KV 存储；
- 实验平台；
- 监控系统。

------

## 8. 从服务端工程角度理解搜索引擎

对于 C++ 或 Rust 服务端工程师，搜索系统中最重要的工程能力包括：

- 倒排索引和向量索引；
- 异步 RPC；
- 多路并发召回；
- 分片查询；
- TopK 归并；
- 批量特征读取；
- 缓存；
- 超时和 Deadline；
- 熔断、降级和兜底；
- CPU 与 IO 任务隔离；
- 高吞吐、低延迟服务设计。

可以将搜索引擎概括为：

> 一个以 Query 为入口，通过索引快速召回候选，再经过多阶段排序，在严格延迟预算内返回高质量结果的分布式系统。

------

## 9. 最终记忆模型

```text
用户输入 Query
    ↓
理解用户想找什么
    ↓
从索引中召回候选
    ↓
筛选并排序候选
    ↓
加入业务规则和多样性
    ↓
返回最终结果
```

框架层面可以这样记忆：

```text
Elasticsearch：最常见的完整搜索平台
Solr：成熟的企业搜索平台
OpenSearch：开源搜索与分析平台
Tantivy：Rust 全文检索内核库
```

现阶段不必深入具体算法，先建立下面三个核心认识：

1. 搜索不是简单字符串匹配，而是一条多阶段处理链路；
2. 搜索系统的核心是 Query 理解、召回、排序和低延迟调度；
3. Tantivy 属于搜索内核，Elasticsearch 等属于完整搜索平台。
